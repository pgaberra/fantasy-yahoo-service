# Decision log

Non-obvious choices in this service, one line each. Format and rules: the monorepo root `DECISIONS.md`.

---

[2026-09-11] fantasy-yahoo-service: an unknown path answers 404 through its own `NoResourceFoundException` handler, copied from bff and espn-service (fantasy-workspace#33) — a shared advice library was rejected because the services deploy separately and it would couple their releases for about ten lines, and a catch-all that passes every Spring `ErrorResponse` 4xx through quietly was left for a separate decision across all four services rather than widening this fix.
[2026-09-11] fantasy-yahoo-service: the four OAuth secrets are checked by Bean Validation on `YahooOAuthProperties` at binding (#45), including the 32-byte key length — a `@PostConstruct` check like `InternalApiKeyFilter`'s was rejected because it would sit in whichever bean happens to read the value, and a check in the record's constructor because unit tests build the record by hand with blanks; both staging and prod containers were confirmed to carry all four, non-blank, before merging.
[2026-09-11] fantasy-yahoo-service: the sync flag is claimed in `SyncService.startAsync()` before the thread starts, and a busy `sync()` returns empty instead of throwing (#44), ported from espn-service#16 — keeping the controller's `isRunning()` pre-check plus a quieter log was rejected because the check-then-act gap stays open, and the scheduler overlap is a skip at INFO, not a failed run, because the run under way does the same work.
[2026-09-11] fantasy-yahoo-service: only a dedicated `YahooUpstreamException`, thrown by `YahooFantasyClient` and `YahooTokenClient`, maps to 502 (#47) — rewording the config and crypto paths was rejected because it fixes those instances and leaves any future `IllegalStateException` blamed on Yahoo, and `YahooGrantRejectedException` stays separate rather than a subtype because its remedy is re-consent, not retry.
[2026-09-11] fantasy-yahoo-service: local `docker-compose.yml` moves from `postgres:17-alpine` down to `16-alpine` to match what Coolify runs in staging and prod, checked on both servers (#46) — upgrading the servers to 17 was rejected as a data migration on two live databases for no feature this service uses, while a local mismatch can hide a version-specific difference until deploy.
[2026-09-15] fantasy-yahoo-service: a 403 from the Fantasy API becomes `YahooAccessDeniedException` and is answered as 403 with Yahoo's `error.description`, logged at WARN — from 2026-08-26 to 2026-09-15 Yahoo's app-level refusal went out as a 502 "upstream failure" and read as an outage; making it a `YahooUpstreamException` subtype was rejected because the advice would still have to tell the two apart and a refusal's remedy is Yahoo's grant, not a retry, and ERROR was rejected because a user whose own account is refused is not our fault while a lost app permission still reaches ERROR through the sync's failed run. The token endpoint's failures are unchanged.
[2026-09-16] fantasy-yahoo-service: the OAuth callback parks tokens under a one-time link code that the signed-in web claims through the BFF, and only the user who started the flow may claim it (a different user's claim discards them) — a cookie set on yahoo.slapstat.com by a start redirect was rejected because it needs a second public route on that host, and binding the state to a browser the web holds cannot work since the callback runs on another host; the code rides in the URL fragment so no server log or Referer sees it.
[2026-09-16] fantasy-yahoo-service: the container runs as `app` with a fixed UID/GID of 10001, given numerically to `USER`, instead of root — the base image's existing `ubuntu` user (1000) was rejected as an account the image's maintainers own and may change, and handing the user a writable `/app` was rejected because the service writes only to `java.io.tmpdir` (/tmp), so the unpacked jars stay root-owned and read-only to it.
[2026-09-17] fantasy-yahoo-service: the connection status reports not connected when the stored refresh token cannot be decrypted, logged at WARN, and still keeps the row — after the 2026-09-16 key rotation staging showed Yahoo as connected while every league call failed; deleting the unreadable row was rejected because a key that is only wrong for a while would cost every user their connection, and ERROR on the status check was rejected because it runs on every page view while the ERROR a wrong key needs is already raised where the token is used.
[2026-09-17] fantasy-yahoo-service: `GET /api/v1/yahoo/leagues/{key}/free-agents` reads Yahoo's `status=A` (free agents and waivers together) sorted by actual rank, capped at a `limit` the service enforces on the response as well as in the request, and reports `availability` per player (fantasy-web#751) — `status=FA` alone was rejected because it hides the player a rival dropped an hour ago, which is the one a streamer most often wants; the cap rides on the rank sort so a trimmed list loses the tail nobody streams, and it is re-checked while parsing because Yahoo has served fuller pages than `count` asked for.
[2026-09-22] fantasy-yahoo-service: `GET /leagues/{key}/teams` returns the teams in draft order, read from the draft results (the one `out=settings,draftresults,teams` call the draft endpoint makes), because the draft setup imports teams from it and Yahoo's `/teams` lists them by team id — rejected: having the web's setup read `/draft` instead, which is behind DRAFT_LEAGUE_SYNC_ENABLED and would leave every consumer of `/teams` with the wrong order.
